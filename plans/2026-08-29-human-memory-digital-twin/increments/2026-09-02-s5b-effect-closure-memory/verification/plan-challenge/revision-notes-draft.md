# Plan 修订草稿（synthesis 前的工作笔记；正式修订以 challenge-synthesis.json 为准）

## 已由 specialist 实证确认、修法确定（closure-terminal-window / analysis-idempotency-lineage）

1. **去掉 Harness 证据 outbox+异步 worker**（harness-evidence-outbox-async-vs-run-terminal-ordering）：
   state.db 内提交的事实（snapshot receipt / route decision / route tool invocation）在同一事务直写 `ExecutionEvidenceIngress`；
   其它 DB 事实（SDK effect、provider invocation）先在 v46 `harness_evidence_reservations(run_id, source_sequence UNIQUE, source_event_id UNIQUE, status reserved|ingested|abandoned)` 预留 seq，
   物理动作完成后 ingest；terminal observer = 唯一排空者（run_terminal 前按 seq 顺序 ingest 或 tombstone 全部 reserved），`next_sequence = MAX(reservations ∪ receipts)+1`；crash 后新 owner 重放同一排空（source_event_id 幂等）。
2. **兜底窗口 durable 状态机**（closure-fallback-window-durable-state-and-recovery）：
   v46 `post_turn_invocation_attempts(attempt_id, purpose, host_run_id, sdk_run_id, generation, task_scope_id, closure_watermark, request_hash, attempt_ordinal, status reserved|handed_off|succeeded|failed|unknown, unknown_class, provider_request_id, plan_id, created_at)`，`UNIQUE(request_hash, attempt_ordinal)`；
   closure request_hash = H(sdk_run_id, task_scope_id, closure_watermark, last_assistant_message_hash)，plan_id = H(request_hash)；只有当前 lease owner 可调 Provider（reserved 行与 `_validate_lease_tx` 同事务；新增 `EffectBoundary.CLOSURE`；返回后再 `_validate_lease_tx` 才 apply）；
   reconcile：无行/failed(not_sent) → 新 ordinal；reserved 未 handed_off → 标 failed(not_sent) 后新建；handed_off/unknown → **绝不重发**，终结为 pending(closure_attempt_unknown)；succeeded 无 receipt → 从 `task_scope_mutation_decisions` 按 plan_id 派生 receipt；receipt 与 `apply_mutation_plan` 同事务；终态门对 COMPLETED/FAILED/CANCELLED/STOPPED 一律生效，兜底只在 COMPLETED 且有 staged answer 时发。
   **终答交付点**：终答由 SDK delivery pump 在 Host 终态前交付（kernel_terminal.py:160-180 / delivery.py:129-190），"暂存终答不交付" 不可在该 seam 实现 → 改为 **D1 修订**：终答按既有 pump 交付；closure 兜底在 Host 终态前完成，pending 标记由 Host 终态 receipt/STATUS 投影承载并在下一轮 snapshot 注入（用户确认）。
3. **pending 归属 = admission scope**（pending-closure-bound-to-scope-not-conversation）：每个 foreground Run 在 admission 时绑 scope（`QueueTurnRequest.scope_ref` 必填）；`task_scope_closure_receipts(task_scope_id, sdk_run_id, closure_watermark, outcome mutate|no_mutation|pending, plan_id, reason)`；dirty 按 scope 自最后非 pending receipt 的 watermark 起计算 → 下一个进入同 scope 的 Run 合并前序 pending；跨 Run 提交 base_revision 取提交时 head、evidence_refs 允许该 scope 已链接的 evidence；路由到其它 scope/standalone 的轮不承担也不清除；scope complete/checkpoint/resume 时仍 pending → Host 确定性 `no_mutation(closure_reason=closure_abandoned, reason_code=host_forced)` 零 Provider 调用，STATUS 显式展示 `semantic_closure_pending`；状态迁移表：pending→no_mutation 任何 status 合法边，complete 之后禁 plan.* 操作（store `_reduce` 不拦，Host 侧拦）。
   附带：`append_host_event` 不产 `human_memory_evidence` 行 → 客观事件必须同事务写 evidence 行（refs 才可用）。
4. **task_scope_update 始终暴露**（task-scope-update-projectless-safe-vs-dirty-exposure）：direct 工具 + PROJECTLESS_SAFE；policy = non_project_effect / route required / task_scope required（UNROUTED 首轮由 barrier 拒）；handler 级门：standalone → `task_scope_update_scope_unbound`；无脏/pending → `task_scope_update_nothing_to_close`（不递增 revision）；snapshot 注入只控制指令文本。
5. **analysis 幂等账本键**（analysis-idempotency-attempt-bound-unknown）：`UNIQUE(request_hash, attempt)` + attempt 无关的 `evidence_set_key = sha256(request.to_json() − {job_id, attempt, idempotency_key})` + per-member `(subject, run_id, evidence_id)` 索引；任一成员存在 open `handed_off`/`sent_unknown` 行 → 拒绝再投递，0 Provider 调用；`sent_unknown` 在非流式 OpenAI 兼容端点无生产确认路径 → 可执行终态 = 拒绝每次再投递 → Memory `dead_letter(analysis_executor_failed)` after max_attempts + Host durable `memory.analysis.blocked{reason}` 事件；`sent_confirmed` 仅经注入的测试 reconciliation observer 可达（S5B-S3 lane 必含）；**lease_seconds 必须 > analysis deadline + 余量**（A1 实测 16.6–33.9s，30s 不够）；re-delivered `handed_off` 行 → await/refuse，绝不再派。
6. **lineage 绑在 ingest**（analysis-request-lineage-worker-config-not-run-binding）：Memory 0.6.1 `ingest_committed_evidence(..., analysis_lineage=AnalysisLineage(provider_id, model_id, model_config_hash))` 逐 evidence 持久；`claim_analysis_batch` 从成员派生并断言一致（同 run_id 检查）；Host `model_config_hash = sha256(canonical{provider_id, provider_incarnation_id, provider_config_revision, model_id, model_params, endpoint_identity})` 于终态提交同事务写入 outbox 行；executor 校验 request lineage == 重建的 binding，否则 blocked；0.6.0 里程碑期间以"单 worker 镜像当前 binding + executor 校验"作显式中间态。
7. **binding 不可重建终态**（analysis-adapter-rebuild-after-provider-config-change）：`not_sent(reason=binding_unrebuildable: provider_removed|incarnation_changed|config_revision_changed)`，0 Provider 调用；Memory max_attempts 后 dead_letter（或 0.6.1 `AnalysisExecutorPermanentError` 立即）；Host durable `memory.analysis.dead_letter{run_id, evidence_set_key, reason}`；不自动在新 binding 下重分析（96-97）。

## effect-gate-exposure（specialist 已实证，17 passed spike）

8. **拒绝/故障二分（effect-exposure-hiding-unverified-and-standalone-run-fault，确认）**：冻结 SDK 只有两条模型可见拒绝（`MODEL_AUTHORITY_FIELD_FORBIDDEN`、`ROUTE_BARRIER_NOT_OBSERVED`，均在 preflight）；standalone 路由下的 PROJECT_EFFECT、零/多 root、hidden/deferred 工具全部是 `driver_failed` 整 Run 故障（`sdk_task_execution_route_authority_missing` / `sdk_task_execution_root_authority_unavailable` / `catalog_execution_policy_unavailable`）。plan 删除"SDK unknown-tool rejection"与"暴露随路由=拒绝"的说法；明写二分：模型可见 `ToolResult.rejected` = {UNROUTED、同批、伪造 authority 字段、envelope 签发后的 EffectGate 失败}；Run fault（稳定码，Host 映射为 durable FAILED + `host.run_fault` 事件）= {standalone PROJECT_EFFECT、零/多 root、hidden 工具}。route-aware `provider_specs` 隐藏只作降低概率的可选手段（fingerprint 稳定），不承担语义。
9. **envelope root vs 冻结写根分裂（新 P1 effect-envelope-root-vs-frozen-write-scope-split）**：同 Run 再路由到另一 scope 时 envelope 证明 root-B 而 handler 物理写 root-A（冻结 `write_scope_root`）。修法：EffectGate 在 `ProductEffectExecutor.execute` 前解析 `registry.resolve(run_id)` 冻结 authority，断言 `envelope.task_scope_id == authority.task_work_context.task_scope_id`（`effect_gate_frozen_scope_mismatch`）、`workspace_resolution.kind == project_bound`（`effect_gate_projectless_project_effect`）、`verify_task_execution_envelope(...).root.canonical_path == authority.task_work_context.workspace_root`（`effect_gate_frozen_root_mismatch`）。**不**在 context_route 禁止再路由（保留 S5a 五路语义），效果是：再路由到别的 scope 后本 Run 的项目 effect 全部稳定拒绝，下一轮（admission 到新 scope）才可写。D2 措辞据此修订。
10. **Auto 豁免过宽（新 P1 auto-mode-exemption-broader-than-folder-append）**：SDK 授权路径 `decide()` 从不传 `explicit_only`，auto 模式对任何类别合成 `policy:auto` grant；`_CONFIRM_ONLY` 只活在 legacy `harness/tool_executor.py`。修法：EffectGate/`decide()` 从冻结 catalog 的 effect 分类（`IrreversibleEffectPolicy.classify` / manifest dangerous）计算 `explicit_only`，`plan_prepared_call(explicit_only=True, confirmed=False)` → auto 下返回 REQUIRE_USER（`product_policy_user_confirmation`）；断言测试 (a) auto+DESTRUCTIVE → REQUIRE_USER 且 grant_source ≠ policy:auto；(b) auto+write_file（REVERSIBLE_LOCAL）→ ALLOW（既有 auto 策略，preserve-approved；AC-3⑤ 措辞改为"Auto 豁免 folder-append 确认并沿用既有可逆本地效果的 auto 策略；_CONFIRM_ONLY 类永不 auto-grant"）；(c) auto+append_binding 无 manual challenge；(d) PROJECT_EFFECT 清单逐项有冻结 EffectClass，confirm-only 子集按名断言。
11. **scope-change proposal（tc-hm-09-multi-root-canary-vs-oos-and-d2-wording）→ 交用户**：(a) S5B-S4 以"每个 canary root 一个单 root scope"跑 TC-HM-09 步骤 6，并断言两 root scope 稳定 fail-closed（AC-3② reason）；以 verification-spec 的 oracle 解释 + `behavior_changes` 入账，TC-HM-09 不改；(b) Run 内 Manual append 之后的 effect 语义取 **strict**：head ≠ receipt → `workspace_binding_receipt_superseded`，直到下一轮 route 刷新；(c) D2 改为"standalone 路由下写工具不可见/不可激活；模型仍调用则本轮以稳定原因 fail-closed 且零写入；建立 TaskScope 后在下一轮执行写入"。
12. **reason-code 表与检查顺序（P2 binding-head-vs-receipt-stale-definition）**：Task 0 冻结：envelope 存在/身份回声（`effect_gate_envelope_missing`/`_identity_mismatch`）→ sticky memo by (run_id, route_receipt_id)（`effect_gate_route_receipt_rejected`）→ 冻结 authority 一致性（三码）→ `verify_task_execution_envelope` S4 码集{route_authority_missing|stale, envelope_lineage_mismatch, effect_authority_missing|stale, envelope_root_mismatch, workspace_root_unavailable, workspace_root_identity_drift, workspace_root_not_canonical, workspace_root_too_broad}→ scope lifecycle（`effect_gate_task_scope_not_active`）→ confirm-only/grant（`product_policy_user_confirmation`）。全部以 `ToolResult.rejected(error_code)` 返回，effect=None（无 execution_effects 行、无 host.file 事件）。注：`exact_receipt` resolver 不查文件系统，inode/canonical 只在 per-effect verify 里跑（这正是 per-effect 重验的价值）。
13. **cutover：PROJECT_EFFECT 分类改变 SDK catalog fingerprint（P2 project-effect-policy-change-breaks-inflight-run-restore）**：v46 迁移前置"无非终态 foreground Run、无 WAITING SDK Run"+ drill；或 bump catalog generation/record version 使 pre-v46 Run restore 走稳定隔离；加"恢复旧 checkpoint → 稳定结果"测试。归 cutover cluster。
