# retro — S5b effect gate / 语义收口 / 记忆分析

## 自我批评（一行制，写给门禁退休评审）

- **调查停在"组件存在"，没停在"端到端可驱动"**：plan 的现状调查给全了 file:line，却从没验证过
  生产入口能不能真把这条链推起来；VALUE_SMOKE_GATE 是靠 pytest 基座手工按序调
  `prepare_candidate/claim_next/record_*/bind_sdk_run` 通过的——基座恰好补上了每一处生产装配缺口，
  于是 9 个既有缺陷全部留到验收阶段才一次性爆出来。**"有代码"不等于"能跑"，冒烟必须走生产接缝。**
- **修之前没确认改的是不是那个处理器**：`file_read`（工具名）的处理器在 `tools/file_tools.py`，
  我改了 `os_tools/read_file.py`，重跑照样红才发现。**按日志里的工具名反查注册表，再动手。**
- **闸门次序反了**：先记录场景、后 re-attest，导致文档改动被 fail-closed 成行为变更，7 场景全部作废重跑。
  **代码冻结 → re-attest → 跑场景 → 记录**，顺序不能颠倒。
- **一度把上游故障和业务失败混为一谈**：provider 502 那轮我先当成"模型抖动"，差点据此放过。
  是查了 `foreground_terminal_receipts` 才分清。**判读证据前先确认哪张表承载业务结论。**
- **我搭的重试循环在系统性过滤不利证据**：它的设计是「收够 2 个通过就停」，于是同一个冻结
  HEAD 上跑了 5 轮、失败 2 轮，账本里只留下通过的那 2 轮，journal 与 RUNLOG 零披露。
  我当时没意识到这是挑证据——但机制的效果就是挑证据，**动机无辜不改变结果**。
  独立复审一眼看穿。已改为固定跑满 N 轮、每轮都入账，并按真实成功率下结论。
- **我在提交信息里写了一条失实声明,而且是关于「我验证过」的声明**：P0-15 那条称
  「变异后 2.2 秒内两条转红」，实际变异改的是测试文件里自己抄的那份控制流副本，
  删掉生产代码后测试照样全绿——那个用例从未守护过任何东西。
  **教训：变异验证必须改生产代码；测试里复刻被测逻辑，等于自己给自己作证。**
- **我把一个真缺陷归因成了模型行为**：某轮记忆零物化，我判「模型判断无可记」并记 INCONCLUSIVE。
  真因是 analysis 响应被 `max_output_tokens` 截断、工具调用发不完整，被代码压成了
  「模型主动放弃」这个理由码。**两种成因共用一个码,是缺陷不是巧合**——而我恰好被它骗了。
  凡是「系统说它成功了但结果为空」，先怀疑分类，别先怀疑模型。
- **可观测性欠账让每次定位都要重造探针**：拒因不入日志、工具参数不落库，本轮三次靠写探针复现机制才定位；
  通过的 root run 里 4 次 `file_read` 失败至今**无法归因**——我如实记了"未能归因"，没有编个说法糊过去。

## 做对的
