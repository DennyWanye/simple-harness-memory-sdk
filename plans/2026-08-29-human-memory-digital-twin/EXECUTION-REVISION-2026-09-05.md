原 acceptance 仍是业务要求基准。本文件直接调整执行顺序；涉及终态语义、预算或 gate 继任协议的具体修改，
须在对应实现前写出新旧契约映射与决定性预期，再版本化接入验收。技术审查由执行者组织，不重新请求方向批准。

## 下一轮的首个可展示结果

启动当前构建，只有一个稳定主对话；普通问题直接回复，不建立假 TaskScope。
再执行一个真实项目任务，能够暂停/恢复或结束；重启后仍能看到实际历史，后续消息不会被坏队首永久挡住。
然后在同一入口完成「记住偏好 → 后续需要时使用 → 纠正 → 忘记后不再使用」。
每一段只有通过对应真实链路验证才标完成，不以 store/DTO/admission 的单测代替运行闭环。

## 收口成本：先固定契约，再改状态机

- 明确三个独立事实：外部执行结果已持久化、TaskScope 语义整理状态、Memory 分析状态。待整理不能伪装成已应用。
- 为语义补交固定有限次数、累计等待 deadline、输入/输出 token 上限；预算从首次补交持久化，重启不重置。
- 起始设计优先评估至多一次额外语义补交；具体时限和 token 数从现有 Provider 约束与小型故障验证确定，
  写入版本化验收预期后再实现。不是现在声称任意 Provider 都能满足某个未经验证的秒数。
- 上限耗尽后保存待处理原因和明确恢复入口；未知调用不盲目重发，不能因释放 UI/FIFO 而重复副作用。
- 依赖尚未完成语义整理的同 TaskScope 后续执行仍有 freshness/状态门；无依赖的普通消息是否可继续，
  必须由显式状态转换证明，不能简单跳过现有 terminal gate。
- 普通 Memory 分析仍批量异步；记录每条业务链新增 Provider 次数、耗时和 token/费用，优先消除重复调用。
  本次不以节约成本为名直接更换已绑定的主模型或放宽 mutation authority。

## 验收工具与测试成本

1. 按产品缺陷、fixture/oracle 缺口、执行器未实现、外部依赖分类剩余 BLOCKED，不把数量当产品缺陷数。
2. 先决定性自动化/公共 API/独立代码审查，再做真实 UI/provider。一次真实运行当场登记，不为登记重复调用。
3. 修复 gate 对当前候选、验收修订、继任关系的识别：保留旧失败历史，同一候选的失败不能被新目录洗掉；
   已获批准的修订须有可验证映射。先用历史账本副本作回归 fixture，不直接修改活动账本或全局安装的 skill。
4. 稳定性按同一候选与同一有效验收契约统计；跨版本失败保留在历史报告，不伪装成当前版本的随机失败。
5. 只复测变更影响到的层；完整候选就绪再执行必要的全量和 program 真机矩阵。
6. 功能实测状态与工具状态分别报告。工具未修好不伪造 receipt；功能通过也不冒称原 program 全部通过。
